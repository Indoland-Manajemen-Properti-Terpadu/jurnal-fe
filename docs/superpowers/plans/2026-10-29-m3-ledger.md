# Milestone 3 (Ledger) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax. **One agent at a time** (the developer laptop has 8 GB RAM; two concurrent gates killed the editor twice). Prefix node commands with `NODE_OPTIONS=--max-old-space-size=1536`.

**Goal:** Split `src/module/GeneralJournal` (123 files, 16.7k lines, zero tests) into seven feature modules on a small shared accounting kernel, without changing any accounting outcome, and release it as R2.

**Architecture:** Strangler migration. First pin the accounting invariants with tests and extract a pure kernel (`src/lib/accounting`) plus the account hub API that 20 outside files depend on. Then move one sub-feature per PR in dependency order; old paths keep working through re-export shims until the last PR removes them.

**Tech Stack:** React 18, TypeScript strict, Mantine 8, TanStack Query 5, Zustand, Vitest, `@/lib/money` (integer minor units), ESLint ratchet.

**Spec:** [`../specs/2026-10-29-codebase-restructure-design.md`](../specs/2026-10-29-codebase-restructure-design.md) sections 4.3, 5, 8. Procedure, constraints and gate: [`2026-10-29-m1-small-modules.md`](2026-10-29-m1-small-modules.md) ("Global Constraints", "Module Migration Procedure"); this plan only adds what differs. Evidence: a read-only audit of the module (2026-10-29), cited below as `GJ/path:line` where `GJ = src/module/GeneralJournal`.

## Why this order and not the one in the spec

The spec listed `chart-of-accounts` first. The audit shows that is unsafe: `JournalAccount` (Edit) imports `DetailAccount/Main` (`useDetailAccount`) while `DetailAccount/Main` imports `JournalAccount` (`useDeleteJurnalAccount`, services, hook): a cycle, and `useJournalAccounts` is the hub for 20 files in six other modules. Moving it first would either break those or leave a cycle across new module boundaries. So the order is: kernel and account hub API, then the leaves (fewest incoming dependencies), then the hub (`account-ledger`) last.

## Global Constraints

- All constraints of the M1 plan apply (English names, kebab-case, layers only where real, i18n `id` and `en`, no `any`/`console`, files at most 400 lines, no cross-feature deep imports, ratchet may only go down, Conventional Commits with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`, move commit first).
- **Accounting outcomes are frozen:** every invariant in the table below must give the same result before and after, proven by a test written against the old code first. Rounded half up to the cent at input boundaries (as in `purchases` and `assets`); whole-rupiah data must be identical.
- Do not invent features: where the client does not enforce something today (see "Not enforced today"), the migration does not add enforcement. It is listed for the user to decide.
- Error handling follows the M1 rule: migrated code uses the default `apiClient` and lets errors reach TanStack Query. This **fixes** today's false success toasts (see Rulings R3) and is called out in each PR.
- No endpoint, payload or query-key semantics change, except the dead or colliding query keys listed in R5.
- Every PR gets an accounting review pass before merge: the agent (or I) re-reads the PR diff against the invariant table and, where useful, the `finance:journal-entry` / `finance:reconciliation` skills as a checklist lens. The result goes in the PR body.

## Not enforced today (not added by this migration; for the user to decide)

No closed-period or lock-date check on create or delete; no account code format or uniqueness check; no block on posting to header, archived or inactive accounts; no future-date guard; no decimal-precision policy beyond what the inputs allow; no journal edit or reversal; no opening-balance cut-off versus earliest-journal check; no guard against double counting a parent and its children in beginning balances; bank-statement import sends invalid rows (only a warning); journal create treats only HTTP 200 as success.

## Rulings made while planning

- **R1 Kernel location.** Pure accounting rules live in `src/lib/accounting/` (no React, no HTTP): `normalBalance.ts` (I5), `journalBalance.ts` (I1, I3, using `@/lib/money`), `accountTypes.ts`. Reason: four modules need them and `lib` is the existing home of pure shared code; a feature module would force cross-feature imports. Cost if wrong: move the folder.
- **R2 Account hub API.** `useJournalAccounts`, `getJournalAccounts`, the `JournalAccounts` type and `useDeleteJurnalAccount` become the public API of `chart-of-accounts`. Task 1 creates the module with just these and a re-export shim at the old paths, then retargets the 20 outside importers. Cost if wrong: one more shim.
- **R3 False success toasts are bugs, fixed.** `post/patch/del` swallow errors, so add, update, delete and archive of accounts and several journal actions show a green toast and navigate on failure. Migrated code throws; the success/failure toasts now match the result. This is a user-visible behavior change in every module PR and is called out as such.
- **R4 `period-closing` is a prototype.** `PeriodeLockAndClosingBooks` has no HTTP at all (mock modal, fake select data, hard-coded date text, copy-pasted toasts; `KeyPeriod.tsx` is 0 bytes). It is migrated structurally and translated, never presented as working: the README says "UI prototype, no backend". Whether to build the backend or hide the pages is a decision for the user.
- **R5 Query keys.** The dead invalidations (`get_journal_details_for_recon`, `journalAccounts`, `journal_accounts`, `head_accounts`, `journal_transactions`) are repointed to the real keys in the owning module, and the colliding `transaction_by_account` shapes get distinct keys. This makes lists refresh after mutations, which they did not. Called out in the PR.
- **R6 Tolerance.** I3's `0.01` view tolerance and I1's exact equality both become integer equality in minor units (identical for data with at most two decimals). The inconsistency is documented, not widened.
- **R7 Bugs fixed in passing, each with a test and a PR note:** `GJ/Main/pages/GeneralJournalPage.tsx:203` navigates to `bankStatementDraftImport` without substituting `:idAccount`; file download returns an error body that is saved as `.xlsx` (check status first). Not fixed, only documented: detail tab ignores `?tab=` (BankCash links to it), `POST_COMMIT_IMPORT_BANK_STATEMENT` builds `/v1/bank-statement//:id`, junk toast text "Failed asdasd", journal attachments as JSON.
- **R8 Misspelled public names** (`useBeginingBalance`, `useDeleteJurnalAccount`, `IncomeStatmentTable`, `BankStatamentTabs`, `PeriodeLock`) are renamed inside the migrating PR together with all their importers; nothing outside `GeneralJournal` and the listed importers uses them.
- **R9 Dead code** listed by the audit is deleted in the module PR that owns it, after grep shows no importer (`BankStatement/pages/ImportBankStatement.tsx`, `pages/BankStatement.tsx`, `SettingAccount/components/ImportModal.tsx`, `JournalAccount/store/useAccountImport.store.ts`, `JournalAccount/store/useAccount.ts`, `Main/services/SelectionHandler.ts`, `BadgeAction.tsx`, `DeleteAllButton.tsx`, `store/GeneralJournal/addJournalAccount.tsx`, `ImportFile.tsx`, `KeyPeriod.tsx`). `CashMapping.tsx` is a 113-line mock: moves to `chart-of-accounts` as-is and is documented as a mock.
