# chart-of-accounts

Chart of accounts: account list, add/edit account forms, account detail query, settings (import, export, restore) and the cash mapping tab. Task 6 PR (a) moved everything here from `GeneralJournal`; PR (b) extracted the account rules and split the add/edit forms; PR (c) made the account mutations throw, fixed the file download, split the last large files and moved every string to i18n.

- **Public API (`index.ts`):** `useJournalAccounts`, `getJournalAccounts`, `JournalAccounts`, `useDeleteAccount` (was `useDeleteJurnalAccount`), `useDetailAccount`, `archiveAccount`, `accountDetailData`, `DetailAccountModel`, `useAccountStore`, `CashMapping`, `canArchiveAccount` and `canDeleteAccount` (used by the account ledger menu). The three route pages are imported by the router from `presentation/pages/*` directly (exporting them from the index creates a cycle with `beginning-balances`).
- **Layout:** `domain/` (types), `infrastructure/` (`accountApi`, `accountDetailApi`, `accountSettingApi`), `presentation/{pages,components,hooks}`.
- **Routes:** unchanged; the router imports the three pages from the index.
- **Endpoints:** `API_ACCOUNT.*` (list, detail, archive, delete, category, create, update, import/export/restore).
- **State:** query keys `['accounts', showArchived]`, `['detail_account', id]`, `['category_account']` and `['category_info', id]`; selection store `useAccountStore` (zustand). Add, update, delete, import commit and reset invalidate `['accounts']` (the dead `journal_accounts` and `head_accounts` invalidations were removed, R5).
- **Cash mapping:** `CashMapping` is a mock (static data), kept as is.
- **Domain rules (`domain/accountRules.ts`, pure, tested):**
  - I5 normal balance: `resolveEffectiveDebit` goes through the kernel `isDebitNormal` (`@/lib/accounting`): category `isDebit` (debit when unset), flipped for a contra account. No keyword fallback on the create form.
  - I6 create: name at least 3 characters (`validateCreateName`), code and category required, a Sub account requires `headAccountId`, a Single or Sub account with a restricted scope needs members (`isHierarchyAndAccessValid`); only a Header account is always visible to all users (`accountHasAccessChoice`), so a restricted Sub account is allowed (the backend accepts it) and the form warns that its balance still rolls up into the parent. Edit keeps a weaker name rule (non-empty, `validateEditName`): the 3-character rule is create only, kept as is. `isCashBankCategory` auto-sets `isBankAndCash` from category `KB` or a name with "kas"/"bank"; `getCategoryPrefix` (kernel `accountTypes`, re-exported) is the code prefix map by category.
  - I7 locked accounts: `isAccountSelectable` (used by the account table), `canDeleteAccount`, `canArchiveAccount` and `canEditAccount` (a locked account cannot be edited: the edit page shows every field read-only through `FormLock`, hides the readiness checklist and the save button, ignores a save, and the ledger header and the cash and bank row disable their Edit entry). Delete and archive are only reachable through the selection, so the predicates are not called there yet.
  - Also pure: `buildAccountPayload` (one payload for create and update), `mapAccountDetailToFormState`, `groupCategoryOptions`, `ACCOUNT_PRESETS` (quick templates; the short keyword `ap` also matches "Pendapatan", kept).
- **Form layout:** the add and edit pages share one layout and the same sections in `presentation/components/account-form/`: `AccountIdentitySection` (presets only when creating, category locked for a locked account), `AccountHierarchySection` (`isEdit` changes the tree labels), `AccountAccessSection`, `AccountReadinessCard`, plus `AccountPreviewCard`; the right column is preview, readiness checklist and the save button on both. `hooks/useAccountFormOptions`, `useAccountPlacementState` (it also clears the parent or child that no longer applies when the type changes) and `useAccountCategoryOptions` are shared. Differences are data only: edit loads the detail, keeps the 1-character name rule and hides the hierarchy card for a locked account. `AccountingGuideCard` is no longer used by either page, and `AddAccountSummaryStrip` was already unused.
- **Errors (R3):** `createAccount`, `updateAccount`, `deleteAccounts` (`infrastructure/accountApi`), `archiveAccount` (`accountDetailApi`) and the settings calls use the default `apiClient`, so an HTTP error rejects and reaches TanStack Query. Before, `post/patch/del` returned the error response, so a failed save showed the green toast and navigated away. Failure toasts show the server `message` when there is one. Endpoints, payloads and query keys are unchanged.
- **Downloads (R7):** the template and export downloads use `apiClient.get(..., { responseType: 'blob' })`; an HTTP error rejects (and a status of 400 or more throws) instead of saving the error body as `.xlsx`.
- **Account table (list page):** one flat `Table` (same pattern as the contacts table) instead of a table nested per parent, so there is a single selection model. `domain/accountTree.ts` (pure, tested) builds the tree: tab, category and search apply to every level, so under the locked tab a locked parent shows only its locked sub accounts. A parent that does not match but has a matching descendant stays as a muted, unselectable context row. Any active filter opens every parent; the chevron and the header button toggle expansion until the filter changes. Select all picks every selectable (open and matching) account in the filtered tree, collapsed or not; a parent checkbox picks its own and its open descendants (indeterminate when partial). The selection is pruned to what the table lists, so a hidden account is never deleted, and it is cleared when the page unmounts. The tab counts come from `countAccountStats` (all levels), the rows from the filtered tree.
- **Edit form hierarchy:** the detail endpoint sends `level` (`master` or `sub`), `subAccount` (children with `id`, `name`, `isLocked`, `isArchived`) and `headerAccount` (`{ id, name, accountNumber }` for a Sub account, `null` otherwise); it has no `headAccountId` or `subAccountId`. `mapAccountDetailToFormState` reads a Sub account from `headerAccount` (or `level === 'sub'`) and a Header account from a non-empty `subAccount` (no child is preselected: existing children are already linked). `useAccountFormOptions` adds `headerAccount` to the parent options because the category info omits a locked parent. The form is filled once per account, so a refetch does not overwrite edits.
- **Overview (list page):** `AccountStatsCards` is four cards, each a number plus a small picture of the same data, drawn with CSS and Mantine `RingProgress`/`Progress` (no chart library, brand primary tints only): total accounts with bars per class (first digit of the code, 1-8, the biggest class in the solid tone) and the parent and sub split; cash and bank as a donut of its share; active categories as a two-segment bar with the balance sheet (1-3) and profit and loss (4-8) counts; locked accounts as a progress bar with its share. The hints add information the picture does not show, they do not repeat it. `countAccountStats` (with `classCounts`) and `percentOf` are pure and tested; `AccountStatsCards.test.tsx` pins the pictures and the zero case. The table has a minimum width per column, so a badge column cannot shrink to "D...".
- **Default tax:** the form field `defaultTax` holds a tax id. The options come from `GET /v1/taxes?limit=100` (`infrastructure/taxOptionApi`, `useTaxOptions`; read here instead of through `settings`, which already imports this module). Create and update send `defaultTax` as the id, or `null` to clear it (the old `taxType` code list is gone). List and detail return `defaultTax` as `{ id, name, rate, taxCode }` (`null` when unset); the table shows its name and the edit form reads its id.
- **Simple accounts:** `useSimpleAccounts` (public API) reads `GET /v1/accounts/simple` (key `['accounts', 'simple']`, so account mutations refresh it): a flat list of postable accounts (`id`, `name`, `accountNumber`, `normalBalance`, `isContra`) without balances, category or header accounts. The journal entry line picker uses it.
- **Large files:** `AccountListPage` uses `AccountStatsCards`, `AccountListHeaderActions` and `domain/accountStats`; the import wizard is `ImportAccountWizardModal` (state) plus `ImportUploadStep`, `ImportPreviewStep`, `ImportDoneStep` and `domain/importPreview`; `SettingAccountModal` renders three `SettingActionCard`s (themes in `settingActionThemes`).
- **i18n:** namespace `chartOfAccounts` (`src/i18n/locales/{id,en}/chartOfAccounts*.ts`, split into `List`, `Form` and `Guide` files that one `chartOfAccounts.ts` spreads; key-parity test in `src/i18n/locales/chartOfAccounts.test.ts`). Groups: `list`, `table`, `settings` (modal, import, export, restore, toast, error), `form` (add form and preview, keys moved from `journal`), `edit`, `guide`, `validation`, `presetNames`, `toast`, `cashMapping`. Domain validators return a key such as `validation.nameMin`; the page translates it. Preset keywords (`ap`, `kb`, `kas`...) stay Indonesian because they match backend category names.
- **Known gaps (not changed, for the owner to decide):**
  - Edit only requires a non-empty name (`validateEditName`); the 3-character rule is create only.
  - The preset keyword `ap` (receivable) also matches "Pendapatan" and other names containing it.
  - `CashMapping` is a mock: static rows, selects that do nothing, no HTTP. It is translated like the rest but still mock data.
  - `canDeleteAccount` and `canArchiveAccount` are called by the `account-ledger` header menu; the list itself only reaches delete and archive through the selection (locked rows cannot be selected).
  - R7 (resolved): the "import bank statement" item was removed from the list header menu (it navigated with the `:idAccount` placeholder unfilled). The working entry is the import modal in the reconciliation tab of a cash/bank account.
  - Strings that were English in the code (delete toasts, `CashMapping` headers, "Unnamed category" and "Unnamed Role") keep that text as the `id` value; they still need an Indonesian wording.
  - Archiving from the detail pages refetches `['detail_account', id]` but not `['accounts']`.
  - The journal namespace keeps the old form keys (other modules may use them); this module no longer reads them.
