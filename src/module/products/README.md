# products

Catalog of goods and services, plus the two master lists that feed it (product categories and units). Each product carries its default selling, buying and inventory settings: accounts, tax, unit price and minimum stock.

- **Routes:** `routes.products.main` (`/products`, list with Products / Categories / Units tabs) and `routes.products.detail` (`/products/:id`). The router wraps both pages in `AppShellLayout`; the pages do not render it (same approach as `pending-changes`, so `AppShellLayout -> Navbar -> module -> page` cannot become an import cycle).
- **Public API (`index.ts`):** `ProductsPage`, `ProductDetailPage`, and `fetchProducts` / `fetchTaxes` (used by the Sale module). `MasterDataPanel` and `ModuleHeader` are generic but no other module imports them, so they stay internal in `presentation/components`; if another module needs them, export them from `index.ts` (do not move them to `src/components`).
- **Endpoints** (`infrastructure/productApi.ts`, `PRODUCT_ENDPOINTS`):
  - `GET /v1/products` (`page`, `limit`, `search`), `GET|PUT|DELETE /v1/products/:id`, `POST /v1/products`. Create and update send `multipart/form-data` (`buyingInfo[...]`, `sellingInfo[...]`, `inventoryInfo[...]`, optional `image`).
  - `GET|POST /v1/product-categories`, `DELETE /v1/product-categories/:id`
  - `GET|POST /v1/units`, `DELETE /v1/units/:id`
  - `GET /v1/taxes`
  - Chart of accounts for the account selects: `API_ACCOUNT.GET_ALL_ACCOUNT` from `src/lib/http/endpoints.ts` (the same call the journal module makes, now done here instead of importing the GeneralJournal service).
- **Layers:** `domain/` (entity types, `productFormat`, `productRules`), `infrastructure/` (API calls, DTOs with legacy field aliases, mapper), `presentation/hooks` (TanStack Query hooks, form hook, reference label hook), `presentation/components` (table, form and its sections, image panel, master data panel and modal, detail header / settings cards / audit panel, stats, toolbar), `presentation/pages`.

## Domain rules

- Section switches: a product can be sold, bought and stock tracked independently. When a section is off, its price, account and tax are not sent. New products default to sold and bought, not tracked.
- Required while a section is on: selling price, sales account and receivable account (sales); buying price and purchase account (purchasing); inventory account (inventory). Name and category are always required. SKU is generated by the API when empty.
- API references to accounts and taxes may be an id or an embedded object; the mapper reduces them to ids and the detail page resolves them to labels (`resolveAccountLabel`, `resolveTaxLabel`), falling back to the raw id, then to "not set" / "tax free".
- Images: up to 2 MB, one file, image MIME types.
- Prices are display-formatted only (`formatPrice`: IDR, at most 2 decimals, `—` for missing). Values are sent to the API exactly as typed.

## Money

No amount arithmetic exists in this module, so `@/lib/money` is not used. Rounding policy for sub-cent values: none. A price such as `10.999` is sent unchanged to the API and only the display rounds it (`formatPrice` shows `Rp 11`); `toMinor` is not applied because it would reject more than two decimals and change what the form accepts today.

## State

- Server data: TanStack Query (`productKeys` in `useProductQueries`; query keys unchanged). Saving or deleting invalidates `['products']`; creating or deleting a category or unit also invalidates its own list.
- Local state: active tab, search, page, page size and modal targets live in the list page; the form uses Mantine form state.

## i18n

Namespace `products` (`id` primary, `en`) in `src/i18n/locales/{id,en}/products.ts`; `src/i18n/locales/products.test.ts` checks identical keys, placeholders and no empty values. Notification texts in the hooks use the imperative `t` from `@/i18n`; form validation messages are resolved when validation runs, so they follow the current language.

## Known gaps

- Pages only know the API through query hooks, but `infrastructure/productApi.ts` is still a flat file of functions (no repository port; there is only one implementation).
- Server-side validation messages come back from the API in whatever language it uses.
- `Sale` imports `fetchProducts` / `fetchTaxes` through this module's `index.ts`, which also loads the product pages; fine today, move them to a thinner entry when Sale is migrated.
- The "System ID (MongoDB)" label and the tax/account placeholder wording are carried over as is.
