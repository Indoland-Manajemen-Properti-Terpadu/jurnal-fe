## Rules the screens follow

- Colour: brand blue and neutrals. Pictures of data use the primary scale; red appears only for real lateness or refusal (payables aging uses one red hue getting stronger). Icon orbs are always primary light.
- Type: Figtree on the type scale, no pixel sizes, no monospace. Amounts use tabular figures, right aligned.

- Amounts shown after saving are the server's; the form estimate (`calculateTotals`) is labelled as an estimate.
- Actions are hidden, not disabled, when the user lacks the right (`usePurchaseAccess`, rights from `/v1/users/me/permissions`) or the status forbids them (`purchaseActions`). The server remains the authority and its refusal is shown politely.
- Approval buttons come from the document's `approval.canDecide`. Submitting or approving never looks like paying: money moves only at `PAID`.
- Reject, cancel and void need a reason of at least 3 characters.
- Files: up to 5 per document, 5 MB each, multipart field `attachments`.
- Error copy never shows server text for validation or unknown failures. Indonesian business messages from the server are shown as written in Indonesian; English readers get a generic sentence.

## Payment Request and Payment Voucher (slice 8/9)

- **Payment Request** (`/v1/purchase-payment-requests`, menu `JP-PURCH-PAYREQ`, approval `JP-PURCH-APR-PAY`). `kind` `DP` takes `purchaseOrder`, `amount` and an optional `advanceAccount` (the server picks one when it is left out); `SETTLEMENT` takes `items[{bill, amount}]` of one vendor. `transactionDate` is required for both. Statuses `DRAFT`, `PENDING_APPROVAL`, `APPROVED`, `REJECTED`, `PROCESSED` (inside a voucher), `PAID`, `CANCELLED`; labels come from `statusLabel` / `kindLabel`, with `APPROVED` now labeled `Menunggu PV` and `PROCESSED` labeled `Menunggu pembayaran`.
- Limits the server enforces with Indonesian business messages (shown to Indonesian readers only): a settlement amount may not exceed the bill's `requestableAmount` (a draft already holds its own amount, so an edit may ask for that part again); all bills share one vendor; a DP cannot exceed `advance.available` of the order and the order's term must use an advance. Zero, empty `items` and a missing `reason` are English field errors (never shown). The form checks the same limits first (`validatePaymentRequestForm`).
- `PUT` rejects `kind` and `purchaseOrder` (400) and keeps omitted fields, so `toPaymentRequestUpdate` sends the whole body without them. Submit, approve (`note`), reject (`reason`) and settlement cancel (`reason`, allowed until a voucher takes the request) are `POST /:id/<action>`. Creating a DP with proforma files sends the draft and attachments together as multipart; a DP draft can still be saved without files, then attachments are added at `POST /v1/purchase-payment-requests/:requestId/attachments` before submit. Both upload paths allow up to 5 files of 5 MB each. The backend checks for any attachment on the request, not a file kind, and does not count order attachments. The FE labels this required file as the vendor proforma and blocks DP submission until one is attached. DP cancellation is exposed only from order detail and uses the order-specific endpoint with `JP-PURCH-DP-CAN`. `canDecide` and `pendingApprovers` drive the approve buttons (the shared `ApprovalPanel`); `segregationOfDuties` is off on the Demo Site.
- **Cancel an order advance** (`POST /purchase-orders/:orderId/advances/:requestId/cancel`, permission `JP-PURCH-DP-CAN` / `delete`) cancels an unpaid `REQUEST`-mode DP and returns the PO/SPK, request and optional voucher. For this mode, `advanceState.billed` is a default flag and does not by itself mean an invoice exists or block the cancel action. The reason is required after trimming and limited to 500 characters. The backend refuses cancellation after any bill history (including voided bills) or payment history (including a later-voided paid voucher), and refuses requests already cancelled or used in a bill. A draft voucher containing only that DP is voided atomically; a combined draft voucher must be voided first. The order detail shows the cancel button only when the role has the permission, the advance and request are not settled, and the order has no bill history; when an otherwise eligible request lacks permission, it explains the missing access. The service remains authoritative for hidden history and combined vouchers.
- List filters: `kind`, `ready=true` (approved and not yet in a voucher), `status` (one or several), `search` (number). `useOrders` takes `vendor`; the new-advance form lists only vendor orders with positive `advance.available`, `advanceState.mode === 'REQUEST'` and `advanceState.paid !== true`. The order list must include `advanceState`; the form fails closed when the state is absent so a paid or bill-route order is not offered for another DP.
- **Payment Voucher** (`/v1/purchase-payments`, menu `JP-PURCH-PAY`): `POST` takes `transactionDate` and `paymentRequests[]` of one vendor, optional `paymentMethod`, `depositAccount`, `referenceNumber`, `memo`. A request that is not approved, or already processed, is refused (400). The voucher has no approval and is `DRAFT`, `PAID` or `VOID`; it cannot be edited (no screen, no route).
- `POST /:id/pay` takes `paidAt`, `depositAccount`, `paymentMethod`, `adminFee`, `referenceNumber`. **Without a deposit account the server pays from a default cash account without a word**, so the pay dialog requires one (bank and cash accounts come from `useSimpleAccounts({ isBankAndCash: true })`). The server refuses a payment date before any settled bill's date, so the dialog starts at the latest bill date (`useVoucherMinDate`). Paying a paid voucher is a 400.
- `POST /:id/void` needs a `reason`; voiding a paid voucher reverses the journal and puts its requests back to `APPROVED`. A paid voucher containing a DP cannot be voided from the FE. `GET /:id/print` is a PDF; files go to `/:id/attachments`.
- Entry points: the bill detail has "Ajukan Pembayaran" (`?bill=`), the order detail menu has "Ajukan Uang Muka" (`?order=`), an approved request opens the voucher form (`?request=`). The sidebar has two entries, Payment Request and Payment Voucher.
- Files: `domain/paymentRequest` (types, form, validation, payloads), `domain/paymentForm` (voucher form, pay form), `infrastructure/purchaseDto` / `purchaseDocumentMappers` / `purchaseApi`, `components/paymentRequests/`, `components/payments/`, `lists/PaymentRequestList`, `lists/PaymentList`, locales `purchasesPaymentRequests` and `purchasesPayments`.

Verified live on the Demo Site (2026-11-21), positive and negative.

- **Return** (`/v1/purchase-returns`, menu `JP-PURCH-RET`: create `c`, post and refund `u`, void `d`; the screens used `JP-PURCH` before). The body takes `settlement` `DEDUCT` (cut the bill), `CREDIT` (vendor credit) or `REFUND` (money back) and an optional `warehouse`; `PUT` carries the whole body without `bill`. `settlementLabel` and `statusLabel` come from the server. The service accepts a return **dated before its bill** and a return of a bill with a missing settlement (it defaults to `DEDUCT`), so the form blocks the early date itself and always sends the settlement. A quantity above what is left, and a missing or short `reason`, are refused; a bill that is already paid starts on `CREDIT` and cannot be deducted. `post` is for drafts only, `void` needs a `reason` (a posted return can be voided too).
- **Refund** (`POST /:id/refund`): `transactionDate` and `depositAccount` are required, `amount` defaults to what is left and may not exceed `creditRemaining` (400 otherwise). It can be paid back in parts; `refundAmount` and `creditRemaining` track it. The dialog requires the receiving account (`useSimpleAccounts({ isBankAndCash: true })`).
- **Vendor credit** (`GET /purchase-bills/vendor-credits?vendor=`): `returns` lists posted returns with credit left, `advances` is empty now that advances go through Payment Requests and are cut at verification. The service lets the remaining credit of a `REFUND` return be applied to a bill too (`POST /purchase-bills/:id/credit-applications`), which lowers what can still be refunded; the screen does not forbid it.
- **Overview** reads the service's own figures: `GET /purchase-dashboard/summary` (counts per stage, procurement routes, ready to pay, and with `JP-PURCH-RPT` the payables with aging), `/actions` ("Perlu tindakan": `title`, `subtitle`, `target {type, id}`, `waiting`, `late`, `due`, already sorted, late first; it holds only what the user may act on) and `/config`. The action wording is Indonesian only, so English readers get a line of ours from the key prefix (`actionPrefix`) and a generic line for a kind that is not known yet.
- **Money precision**: `config.precision` (the decimals of the general settings) is stored in `format.ts` by `useDashboardConfig`, which `PageFrame` calls, so every amount in the purchasing pages follows it. Amount inputs still accept two decimals, and the money maths stays in minor units of two decimals (`@/lib/money`); a site set to more than two decimals would need that library widened first.
- **Document chain** (`GET /purchase-dashboard/chain?type=&id=`, type `purchaseRequest`, `purchaseOrder`, `goodsReceipt`, `purchaseBill`, `paymentRequest`, `purchasePayment` or `purchaseReturn`) replaces the old `usePurchaseJourney` (which stitched the chain from several list calls). Every detail page shows it through `useDocumentChain` and the shared `DocumentJourney`; the return step appears only when a return exists.
- Removed: `usePurchaseJourney`, `useOverviewData`, `usePipelineCounts` and `purchaseOverview` (the client side guess of "what needs action").
- Test data kept: returns RB/2026/11/0001, 0002 and 0003 (voided), RB/2026/11/0004 (posted, `REFUND`, 1.000.000 paid back, 100.000 applied to FKT/2026/11/0004 as credit).

## Screens: shared layout (slice 10)

### PRO-120 purchasing summaries (2026-11-26)

- The dashboard renders the service's `flow` order, due groups, action severity/counts and `oldest`, top vendors, credits, monthly purchases, and procurement breakdown. Action filters page twelve items at a time; the retention card follows the action list in its column to use the available space. Financial sections are absent when the report right is absent; zero values that the service sends remain visible. Retention tasks remain separate from the action feed.
- The payables report reads vendor totals and invoice rows from one `GET /v1/purchase-bills/payables/by-supplier` response. Vendor selection is shared by the visible report, invoice table, and export request. The report uses its returned precision and Jakarta calendar date for the requested `asOf`.
- The request, order, receipt, bill, and payment request lists show four cards from each list response's `data.summary`, above the search and table. Missing summaries are hidden; present zero summaries are shown. The bill's remaining payable card also requires `JP-PURCH-RPT` read access.

### PRO-120 Pesan Ulang PO/SPK (2026-11-26)

- `GET /v1/purchase-orders/reorder-sources` supplies the picker, including blocked completed orders and their reasons. The detail supplies `canReorder`, selectable source lines, the source and related order links, and the live approval plan. Creation requires `JP-PURCH.create`.
- The modal locks vendor, term, warehouse, and source items. Selected quantity and unit price are sent to `POST /:id/reorder/preview`; the server owns totals, price increase, reason requirement, active reorder warning, and approval configuration. Submitting `POST /:id/reorder` uses a UUID reused with the same payload after an uncertain network result.
- Pending and rejected reorders cannot be sent, printed, received, billed, or used for an advance. The detail uses server `canDecide` and the zero-based approval stage for approve/reject, then refreshes purchasing queries.

### PRO-120 Perubahan harga PO/SPK saat faktur (2026-11-27)

Postman `Accounting / All Features` contains the eight request definitions for this flow. The frontend contract is cross-checked against those descriptions and Jira comment #10282; this collection read does not prove live backend runtime behavior.

- `POST /v1/purchase-bills/preview` includes `vendorInvoiceTotal` only as comparison context. Compare it with the server's `total` at returned `precision` (0–4); bill totals, taxes, discounts, payment terms, and due date remain server-owned. A saved PO/SPK bill omits `vendorInvoiceTotal` and hidden discount/due-date overrides.
- A mismatch opens a separate request for one PO/SPK. Send each changed, still-open order item once with its proposed unit price, a required reason (max 2000), and invoice context. An active request or related saved draft can be refused with 409. The bill is not created by submitting a price change; refresh the preview after approval or rejection before saving.
- `GET /v1/purchase-orders/price-changes` lists pending requests. The queue and PO/SPK detail show invoice context, the changed prices, the current approval step, and the approval history. Approve/reject controls require both `JP-PURCH-APR-PRICE.update` and server `canDecide`; decisions send the current zero-based `approvalStage`. A 409 stage conflict requires refreshing the detail.
- The final approval updates order prices and may create backend adjustment journals for received-but-unbilled quantities. The frontend does not calculate or create journal entries; existing order and journal data sources remain authoritative.

All purchasing screens share one set of building blocks in `presentation/components/shared/`: `DocumentFrame` (back link, header card, facts strip, two columns), `SectionCard` (icon tile, title, hairline, body), `InfoGrid`, `AmountsCard`, `RelatedDocsCard`, `DocumentJourney` and `ApprovalTrail` (the approval history sits inside the Persetujuan card, vertical), `ListShell`, `SourcePickerDialog` (the "Buat baru" pickers), `ReasonModal`, and `wizard/*` for the step forms (`WizardCard`, `WizardStepper`, `WizardActionBar`, `ChoiceCard`). Rules every screen follows: tables use `Table.module.css` (no line or empty space under the last row) and rows are the link; a badge is only for a status; notices sit full width under the header; dialogs use `ModalFrame`.

- **Procurement** (FPPBJ detail): route card, steps card (cells follow the route: single vendor has no winner step), quotes card, then reasons and submit. The winner can be picked only when the complete quotes reach the minimum; the reasons and submit cards appear from that point; switching a request to bidding clears a winner kept from the single-vendor route by sending `winner: null` (the service keeps what a PUT omits, so leaving it out changed nothing; `null` is accepted and clears it, verified 2026-11-22). Steps count a winner as done only with enough quotes.
- **Delivery location ("Lokasi kirim") on a request** (QA decision on PRO-108, backend delivered on PRO-116, 2026-11-23): a warehouse select under the department, shown only while a line is goods and required then. It starts on the main warehouse (the warehouse list marks it with `isDefault`; an older request without one gets the main warehouse in the field too) and lists active warehouses plus the one the request already has. The body sends `deliveryWarehouseId` only for goods; for services only it is left out and the service clears the value (checked by editing a draft). The service refuses an inactive warehouse (400 "... tidak aktif") and, when the field is missing on goods, fills the main warehouse itself. The detail page and the submit dialog show it, and the order takes it over (the order draft dialog can still change it before the order goes to the vendor).
- **Warehouse choices come from `GET /v1/warehouses/options`** (PRO-120, 2026-11-24): active warehouses `[{ id, code, name, isDefault }]`, the main one first. The call is open to the stock right or the request right (`JP-PURCH-FPPBJ`), so a requester without stock access can still fill the select; the plain list needed the stock right. The select shows `code · name`.
- **A service receipt (BAPP) carries its signed file** (PRO-120): `POST /v1/goods-receipts` is multipart for a service (`purchaseOrder`, `transactionDate`, `deliveryNote`, `memo`, `items` as a JSON string, and 1 to 5 files of 5 MB in `attachments`); a goods receipt (FPB) stays plain JSON. The BAPP number (`deliveryNote`) and the file are both required, checked on the form and by the service (400 with `data: [{ field, message }]`, "Isi no. BAPP" and "Unggah BAPP bertanda tangan"). The earlier separate "upload the signed BAPP after recording" step is gone; `POST /v1/goods-receipts/:id/attachments` stays for further files.
- **Recurring terms choose their period unit** (PRO-120): a quote with a `recurring` term sends `termOverrides.periodUnit` (`monthly`, `quarterly`, `semiannual`, `yearly`) next to `periods`; it starts on the unit of the master term (`periodUnit` of `GET /payment-terms/options` and of the quote's `termSnapshot`). Custom installment percents of a milestone term keep what was typed when the number of installments changes, and the form shows the live total against 100%.
- **The payment schedule is the service's** (PRO-120): each quote of `procurementView.quotes[]` carries `termSchedule { rows[], percent, amount }` (`kind` `ADVANCE`, `TERM`, `PERIOD`, `RETENTION` or `FULL`; every row is a percent of the whole quote, so they add up to exactly 100, and the amounts add up to the quote total). The quote detail shows it as a table with the service's own sentence per row and never works the figures out itself; a single pay-at-once row is not drawn, because the term name says it already.
- **A DP proforma is sent with its new payment request** (PRO-120): when creating a DP draft with files, the form sends `kind`, `transactionDate`, `purchaseOrder`, `amount`, optional `advanceAccount` and `memo`, and 1–5 `attachments` in one `multipart/form-data` `POST /v1/purchase-payment-requests`. The server creates the draft and attachments atomically. A DP draft may still be saved without a file; it must have at least one attachment before submission. Adding files to an existing draft continues to use `POST /v1/purchase-payment-requests/:id/attachments`.
- **Payment Request values wait for completed approval** (PRO-120): the list and details hide requested, bill, vendor, and advance amounts until status is `APPROVED`, `PROCESSED`, or `PAID`. A cancelled request shows values only when its recorded approval plan proves every level was completed.
- **Payment Request detail** follows the Vercel flow: its route belongs to Pembayaran, settlement rows show allocated and remaining values, and the DP basis reads the payment term from its PO/SPK. A single complete vendor bank account is shown as the destination; when a vendor has multiple complete accounts, the API does not identify which one was selected, so the frontend leaves it blank instead of guessing. An issued voucher and its paid transfer proof appear in their own sections.
- **Rejected vendors** (PRO-108): after an approver turns a winner down the service clears the winner, flags that vendor's quote `rejected: true` and lists it in `procurementView.rejectedWinners[]` (`vendor`, `route`, `amount`, `reason`, `rejectedAt`, `rejectedBy`, `rejectedByInfo { id, name, email, title }`). The screen marks the quote "Ditolak" with who, when and why, disables "Pilih vendor ini", and the service answers 400 if that vendor is chosen again. The vendor dropdown of the quote form leaves out vendors that already have a quote, the rejected ones among them (`excludeIds` of `SupplierSelect`).
- **Request form**: one column "Deskripsi / spesifikasi" (the product picker, then the specification), `Qty`, `Satuan`. The picker lists only goods (stock-tracked products) or only services, following the line's kind, and labels each option Barang or Jasa; a product of the other kind is cleared when the kind changes. There is no free-text name any more, so goods that are not in the catalog are added on the Produk page first (a "Tambah produk" action in the picker was left out on purpose).
- **Bill form** (3 steps): step 1 vendor select (the first vendor is preselected, changing it clears the picks) and a table of receipts or orders with a merge note; step 2 data and two upload boxes (vendor invoice, tax invoice), one file each, sent to `POST /purchase-bills/:id/attachments` with `kind` `VENDOR_INVOICE` / `TAX_INVOICE` once the bill is saved, one after the other (two at once on the same bill make the service answer 400 with a Mongoose `VersionError`, to be fixed by the backend). "Simpan dan Verifikasi" therefore saves a draft first, sends the files, then calls `POST /:id/verify`: creating with `post: true` is refused 400 "Lengkapi data faktur sebelum diverifikasi" because the files are not on the bill yet (PRO fix 2026-11-25). A verify refused with price or total differences asks the question on the saved draft; step 3 lines with the three-way matching reminder and a DPP / PPN / payable preview from `estimateBill` (the service works out the real figures on save). Quantity is read only: the create body carries document ids, not quantities. "Total faktur vendor" stays: with it the service compares the vendor's total with its own (tolerance Rp1) when verifying.
- **Verifying a bill** (QA decision on PRO-111, 2026-11-23): saving a draft stays free, but Verify needs the vendor invoice number, the vendor invoice file, the vendor invoice total on a bill from a receipt, and the tax invoice file when the bill carries VAT (`taxAmount > 0`). `billVerifyMissing` (`domain/billVerify.ts`) lists the gaps; the verify dialog shows them and keeps the button off. Whether the service enforces the same is not confirmed yet (asked on PRO-116); verifying a bill changes data, so it was not tried against the sandbox.
- Summary column of the request, receipt, payment and return forms is 3 of 12 columns.

## Contract facts that differ from the backend document (older documents, to be replaced slice by slice)

Verified against the live service on 2026-11-04:

- `PUT` bodies are not the create bodies. Bill: no `purchaseOrder`; `dueDate: null` is refused. Payment Request: no `kind` or `purchaseOrder`. Return: no `bill`. Each has its own update hook next to its pages (`useUpdateBill`, `useUpdatePurchaseReturn`).
- Reject, cancel and void take `{ reason }`; approve takes an optional `{ note }`.
- Bill variances arrive as `{ type, expected, actual }`; credit applications as `{ source, sourceId, amount, appliedAt, voided }`.
- The payables aging rows carry `vendor: { id, name }`; `usePayablesReport` normalizes them locally.
- A bill does not store its payment term, so editing a draft cannot restore the chosen term.
- Lists sort with `sortBy` (per document) and `sortOrder`. Returns do not accept `endDate`.

## Known gaps

- Who may approve each step (Settings > Alur Persetujuan) is configured elsewhere and is not part of this module.
- Workaround adapters (`billExtras`, the aging normalizer) can be deleted once the shared mappers read those fields directly.
- Request item editor has no "Tambah produk" action (products are added on the Produk page); the barang/jasa split relies on `inventoryInfo.isTracked`, which the service may not mean as goods vs service.
- Bill form: there is no separate due-date column (the term sends the due date), and vendor invoice and tax invoice files are not told apart after saving. Open questions are on PRO-116.

- **Release retention (PRO-128, not committed yet):** the "Lepas" button on the retention task in "Perlu tindakan" opens the dialog "Lepas retensi" (rights `JP-PURCH-RETREL`, only `create`). It sends `{ purchaseOrder, bastNumber, releaseDate, memo? }` to `POST /v1/purchase-bills/retention-releases`, then attaches the signed file to the new bill (kind `OTHER`), and opens the bill. The amounts come from `/retention-releases/preview` (`{ purchaseOrder }` only). The prototype lets the person type the PPh rate; the backend has no such field (the rate follows the term bills), so the field is read-only. Backend gaps: no PPh override, and no file in the release call (so the bill exists even if the upload fails).
